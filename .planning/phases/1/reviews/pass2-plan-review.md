1. **High.** `plan-review-design.md:294` and `:321`, rows H29 and S9. Text at `:91-92`: "mode "state" inside the loop also passes INPUTS_START, the latest tried round when the run began ($docket-in.output.start)". But `filing` (`:294`) and `ready` (`:321`) both pass only `with: { mode: state, slug: <slug> }`. Without START, the ledger cannot compute "next" ("p<1 + LEADING reviews with N > start>", `:106`) or "run_rounds" (`:111`). Two outcomes follow. If START defaults to 0, a rerun counts LEADING reviews and rounds from earlier runs: the slots start past p1, `vacate` can cancel a fresh run on its first round, and the cap fires early. If START is recomputed on each call, the slot never moves after LEADING and the cap and vacancy never fire. Spec review copies the omission (`spec-review-design.md:351`, `:378`).

No node reads "already approved" from the ledger. This breaks 1.3 and 1.4.

3. **Medium.** `plan-review-design.md:95`, row S9 (also `:71-76`, `:26`, `:126`). Text: "A plan is cited when it holds no "[cite:" marker." This is a substring test. `cite.py` uses a marker grammar `[cite: <path> | <quote>]` and does not say how it handles text that does not fit it. Two inputs trip it: a malformed marker (for example `[cite: a.py]` with no `|`), or a resolved quote copied from a code line that contains `[cite:`. In both, `cite.py` exits 0 while the ledger still says owed `defense`. `screen` and every prosecutor are skipped, `case` is "none" ("an iteration with no new review"), the stretch does not grow, and nobody asks the owner. Each iteration spends a fresh Opus `defend` turn until `max_iterations: 200` fails the run. That contradicts `:26` "the loop never ends on max_iterations".
