CHECKPOINT (structural), group G-45, mechanism (i) as RULINGS.md states it: "when `land` finds the checkout moved, it starts a second tree run that runs block `mend` only (rebase, tests, repair) on the existing tree, then asks the land-or-leave gate again; the check repeats if the checkout moves again".

Gap, by documented Archon text:
- The repeat is a cycle: check the checkout, re-mend in a child run, gate, check again at `merge`, re-mend again, and so on with no bound. A re-mend must be a `workflow:` node, because the mend's agents must run with the tree as their checkout and only a sub-run gets one (`workflow-language.md:2073-2083`; `gauntlet-design.md` copy-list bullet "Places a node runs in the tree").
- A `workflow:` node cannot sit in a `loop_group` body: `workflow-language.md:2543-2544` ("Not inside a `loop_group` body ... rejected there at load time (#2439)") and `:1732-1733`, `:1626-1627`. Only `include:` may repeat in a loop body, and an included block has no checkout of its own (`:2612`), so it cannot run in a tree.
- `retry:` is not allowed on a `workflow:` node (`:2056-2057`). A resume re-drives a failed child and threads a finished child's output on; it never starts a second child for the same node id (`:2052-2056`, `:2140-2142`). A fan-out is keyed by item index and is a list fixed at fan-out time (`:2508-2536`), so it makes N children, not "again when the checkout moves".
- So with documented features a run can hold a fixed number of `workflow:` nodes, each started once. "Repeats if the checkout moves again" has no unbounded form. Confidence: high on the doc text (read at the lines quoted); not probed on a live Archon. CLAUDE.md 1.2 applies: a missing Archon feature is the owner's problem.
- Nothing else in the mechanism is blocked. Checked and workable if the cycle is settled: node ids of an included block are `<includeId>__<id>` (`:1591`), so the second tree's branch name uses `sha256("land__retree")[:8]` and `pin.py`'s hard-coded `"tree"` becomes a parameter; a branch pinned at the first branch's tip is a second branch, so Archon reuses it (worktree cut design, "Branch reuse"); the new worktree does not carry the ignored `gauntlet/`, so a copy-in from the first tree is needed; two trees then need removing at landing.

Options for the owner (none applied):
- (A) A fixed number K of re-mend rounds, the round block `include`d K times under distinct ids (each `<id>__retree` a separate `workflow:` node), each round: check, re-mend if moved, gate. Past round K the run stops naming the move. Closest to the ruling; K is a number nobody has ruled, and a stop past K is a stop the ruling does not have.
- (B) One re-mend child before the gate. Inside that child, `include: mend` sits in a `loop_group` that repeats while the checkout's HEAD differs from the head the mend rebased onto (nested `loop_group` is documented as "supported by construction, but is not hardened in v1", `loop-nodes.md:962`). A move during the gate wait still stops at `merge`, as option (a) of the pass-1 record.
- (C) Hold G-45 until Archon runs a `workflow:` node in a loop body (#2439), via a feature request.
- (D) Move the gate and the merge into the tree run, as a loop of `include: mend`, check, show, gate, merge; `gauntlet-run` keeps the record copy and the removal. This is candidate (ii) of the previous checkpoint: it rewrites the Homes rows that forbid the tree run writing the checkout and moves the gate to the tree run's id.
