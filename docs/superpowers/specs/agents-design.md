# Agents for building Gauntlet

Status: approved. Progress against the build order is tracked in [`../../roadmap.md`](../../roadmap.md), "Agents".

## Intent

Gauntlet is built by agents before it can build itself (roadmap rule 5). The user-scope agents in `~/.claude/agents/` were written for other repositories and know nothing of the core/seam split, the quality gates or the blind-review rule. This repository gets its own roster in `.claude/agents/`, one agent per craft, each confined by its body to the layer it may touch.

## Goals

- Specialists all around: an implementer that cannot open the other layer's directory, a test writer that never opens `gauntlet/`, reviewers that are never told what a change is for.
- Each agent provable by one dispatch.
- User-scope `orchestrate` and `lead` route to the roster unchanged: `test-writer` shadows the user-scope agent by name.

## Non-goals

- Replacing `lead`, `hitman`, `ratchet`, `clocksmith`, `hooksmith` or `calibrator`. They fit this repository as they are.
- Any hook or program that enforces the roster. Scope is stated in each agent's body and enforced by nothing else: every agent has `Bash`, so no tool list confines a path. The orchestrator's diff read catches a write outside scope. Nothing catches a read, so every blind rule rests on the body alone.

## Decisions

- `diff-reviewer` gets no purpose line. The quality spec says "without being told what it is for". So it never opens `docs/roadmap.md`, the other specs under `docs/superpowers/specs/`, or the plans under `docs/superpowers/plans/`, where the writing-plans skill puts them: each says what a change is for. Cost: it cannot file scope creep. `test-reviewer` is separate because scope creep in tests is what the bailiff catches later, and this repository's own tests have no bailiff yet.
- Two implementers, not one. The core/seam split is the design's first principle. Each builder's body bars it from the other directory; the diff read catches a write across the split, not a read.
- `test-writer` shadows by name instead of taking a new name. The alternative costs an edit to the user-scope `orchestrate` roster and `lead`.
- `CLAUDE.md` is in scope because `orchestrate` reads the repository roster from there.
- `role-author` comes first and is hand-written, with scope widened from `roles/` to `.claude/agents/` too. Same craft: a prompt for an LLM role with a fixed scope, a fixed answer shape and a refusal rule.
- `spiker` answers one question per dispatch: one open-questions row of the roadmap, or one measurement question an Order step of an approved design names for it, run in a `git archive HEAD` copy it removes and proves removed. A step carrying two questions gets `OVERLOADED:`, and a claim `docs/measured.md` records is not measured again. The role gets the CPU count with `python3 -c 'import os; print(os.cpu_count())'` and caps each run with `perl -e 'alarm shift; exec @ARGV' <cap seconds>`, on macOS and Linux alike. It states that count, each run's cap and their sum before running; suite and mutmut runs in the copy take at most half that CPU count in workers. A cap hit is the finding, never a reason to raise the cap and rerun.
- Stubs are written by the builder that owns the layer, as a `stub` step with no red test, each body `raise NotImplementedError` and nothing else, paths from the plan step (`design.md` §2, stage 6). Package `__init__.py` files belong to the builder of that package; `gauntlet/__init__.py` is `core-builder`'s, since the core exists before any seam. Dependencies and `make` targets are `gatesmith`'s, as `scaffold`, `dependency` and `wire` steps with no red test. A `dependency` step is dispatched together with the step that first imports the package and the two land in one commit, so the dependency gate never sees an unused package.
- `make check-tests` runs each gate of `check` over `tests/` only and fails on any finding under `tests/`. When `FILES` is set, each gate of `check-tests` runs over those files instead of the `tests/` listing. It prints only findings located under `tests/`: the type checkers follow imports into `gauntlet/` as the spec requires, and the target keeps their report to the tester's own files. It is the tester's gate, so no line about `gauntlet/` reaches `test-writer`, which also never quotes one. `make check` is the one entry point for a commit.
- An agent whose `make check` is green on a tree runs no `make check-tests` on that tree: `check-tests` covers nothing more. The quality spec's Gates intro is the authority: "A gate's verdict on a Python file is the same whatever other files the tree holds." `test-writer`'s gate run is `make check-tests` over its own files, `FILES` set to the files it wrote or changed.
- Every heavy run an agent makes, `make check`, `make check-tests`, a suite run or a mutmut run, is wrapped in `uv run python -m gates.heavy`, the host-safety wrapper in `gates/heavy.py`, the same on every host. It holds an exclusive `fcntl.flock` lock on `/tmp/gauntlet-heavy.lock` for the whole of the command it is given, so a second wrapped run waits until the first ends. It takes its lock through `acquire`, the one place it does, handing it stderr: `acquire` asks for the lock without blocking first; when another process holds it, it writes `WAITING`, the one line `heavy: waiting for the lock <path>`, on the stream it is handed, then blocks until it gets the lock, so a test sees the wait as that line. Given `--lock <path>` before its command, it locks that path instead, and the hook entry and every agent's run take the default. `--lock=<path>`, the path after `=` in the same word, is the same option and locks the same path.
  - Given `--lock` with an empty path, it prints its usage and exits 2; where its lock's path cannot be opened or locked, the run is never made: the wrapper prints why and exits 2.
  - One `--` right after the wrapper's own options ends them and is not passed on, so `uv run python -m gates.heavy -- make check` runs `make check`.
  - The wrapper reads its arguments through `parser()`, an argparse parser whose namespace, an `Arguments`, gives the command it runs as `command`.
  - It runs that command at niceness 19, and on Linux at the lowest I/O priority too, by the line `throttle_line(platform, niceness)` of `gates/core/checker.py` gives up to its `--`, followed by the command, where `platform` is the host as `sys.platform` names it, `linux` or `darwin`, and `niceness` is the caller's own and the wrapper passes its process's, read with `os.getpriority(os.PRIO_PROCESS, 0)`: on Linux `ionice -c3 nice -n <k> -- <command>`, on macOS `nice -n <k> -- <command>`, with no `taskpolicy -b`, since macOS's background policy confines a run to the efficiency cores, where `k` is 19 − niceness, since `nice -n` adds to a niceness rather than setting it, and a caller at 19 or above, macOS's ceiling being 20, gets `nice -n 0`; the `--` ends `nice`'s options, so any command is run as given, one whose first word begins with `-` included; each tool is found on `PATH`; on any other host, or where a tool of the line is not on `PATH`, `throttle_line` raises a `GateError`.
  - On any other host, or where a tool of the line is not on `PATH`, the wrapper runs nothing and exits 2, since a heavy run is never made unthrottled. It exits with its command's exit status.
  - Parallel workers queue on one host lock instead of stacking whole suites beside the host's production services.
  - A worker cannot wrap `git commit`, so the lock sits in the hook: the `scaffold` step installs pre-commit with one entry, named `make check`, that runs `uv run python -m gates.heavy make check`. A commit's gate run queues on the same lock as every other heavy run; the hook's output still names `make check`, and its last line is still the evidence a commit was gated.
- `test-writer` sees code under test only as a `stubgen` interface view, never the source, as the tester does in `design.md` §4. The view carries every public name in the module, with signatures and types but no values. `test-writer` cannot see that a stub only raises, so keeping it raise-only belongs to the builder's `stub` step, and checking it belongs to the orchestrator's diff read. mypy is a `scaffold` dependency, so `stubgen` is pinned before the first gate's tests. The summary line still carries an exception's message, so once a module holds real code, a call into it can show a computed value; that residual is accepted. A `NotImplementedError` from another stub the test calls passes the red check the same as one from the stub under test; also accepted.
- A rewrite after an equivalent mutant goes to the agent whose Writes column holds the path, as a `rewrite` step with no red test. The existing tests prove behavior is unchanged; the mutation gate proves the mutant is gone.
- A reviewer finding about how code is built, with no behavior a blind test could reach, would otherwise have no route to a builder, so every builder, `core-builder`, `seam-builder` and `gatesmith`, takes a `finding` step with no red test. Its brief is every upheld reviewer finding from one review round, or every finding one `make check` run reports, naming a `path:line` in its Writes, one or more, each verbatim: a reviewer finding anchored at `path:line` with its failure scenario, a gate finding as the gate printed it, and nothing else. The builder takes them all in one dispatch and handles each as before: it changes the code the finding names, loses no documented behavior, keeps every existing test green and unchanged, and runs `make check` in full. The step lands in a commit of its own whose message quotes each finding. Whether a finding names behavior a blind test can reach is the dispatcher's call, made before dispatch: one that does goes to `test-writer` as a behavior, and the builder takes any upheld, anchored finding it is given without judging that again. Each builder's body holds the step. A finding about how a test is built has the same gap, so `test-writer` takes a `finding` step too. Its brief is every upheld `test-reviewer` finding from one review round, or every finding one `make check` run reports, naming a `path:line` under `tests/`, one or more, each verbatim, and nothing else. `test-writer` takes them all in one dispatch and handles each as before: it changes the test the finding names; every test is green before and after, no test that was red is made to pass, no expected value changes, and there is no red run. The step lands in a commit of its own whose message quotes each finding.
- `test-writer`'s five step shapes are red, `finding`, `repair`, `port` and `moved`; a test step that fits none stops and is reported, and only a design change extends them. `port` and `moved` are two shapes, not one, since their done-checks oppose: `port` keeps every claim and expected value, `moved` changes exactly those a quoted line moved. Only a `moved` step changes an expected value or removes a test, save a red step's `replaces:`.

- A red brief is the word `red` and one or more groups, each `behavior:`, one behavior in the words of the owner or a document; `view:`, the `.pyi` the orchestrator generates with `stubgen` from the stub module into the scratchpad, shared by groups that call one module; and an optional `replaces:`, at most one test id a `port` step reported UNMOVED for this behavior, removed in the dispatch. The groups are one run of consecutive red steps of a design Order, no other step between them, all named as red tests by one build step; a `port`, `moved`, `finding`, `repair` or `stub` step never joins a run, and no run is merged across one. Design Orders keep one red step per behavior, and a lead that needs another merge dispatches the steps one by one. One dispatch writes the run as one diff, in brief order, and starts no behavior once `CHANGED` reaches 300; a behavior whose own tests pass 300 is written whole. Each behavior not started is reported `LEFT` and goes, with its `view:` and `replaces:`, into a further red brief dispatched before the build. A design's file homes still bind a merged brief. Done: each new test red from a run with `--tb=no -rA --assert=plain`, as `AssertionError` or `NotImplementedError`, classified by outcome and exception type. The report adds `BEHAVIOR <n> | <test id>`, `REPLACED <test id> | behavior <n>`, `CHANGED <lines added plus removed over the files written or changed, a new file counted whole>`, checked at the lead's diff read, and `LEFT <n> | <behavior>`. The `finding` step is the one the decision above gives.

- A `repair` brief is the word `repair`; `files:`, at most five paths under `tests/`; `view:`, one scratchpad `stubgen` `.pyi` per own-code module those files import; and `failure:`, each failing test's summary line verbatim. It carries no proposed diagnosis or fix. The lead first adjudicates that the failure comes from test setup, fixture or harness against built code, rather than a broken production claim. In one dispatch, `test-writer` runs the files before, fixes only that test machinery in the named files and runs them after against the same built code. Every claim, expected value and assert statement stays unchanged; no test is removed, skipped, weakened or made independent of the unit. A needed production or claim change is blocked, with no such edit. All tests in the files must pass after; otherwise restore the files to their before text and report blocked. The report carries each failing test and its repair or blocked need, every kept test, before/after summary lines, the diff, the test gate and commands. The lead certifies it as a finding round: reads every diff, verifies preserved claims and assert statements, reruns the reported command and runs `make check` in full before committing. This repairs test machinery in place without setting the build aside or using `replaces:`; it does not change the red-test claim. Proof: a planted wrong-fixture test against a built function is fixed and green in one dispatch, assert lines unchanged; a steered `repair` brief returns `REJECTED: STEERING`.
- A `port` brief moves tests onto what an approved design gives and changes no claim. It is the word `port`; `design:`, an approved design under `docs/superpowers/specs/` and its step number; `files:`, each path under `tests/` the step writes, at most five; and `view:`, one `.pyi` per own-code module the files import. Done: the files' tests green before and after; every test held before is held after, its assert statements unchanged; a helper the design gives is written to the design's stubs, beside its own test file where the design lists one; a test's input changes only where the design step names the change; nothing is written outside `tests/`. Its report adds `KEPT <test id>`, one per test moved, and `UNMOVED <test id> | <the production change it needs>`, one per test the step leaves as it was.
- A `moved` brief changes exactly the tests a document change moved. It is the word `moved`; `lines:`, each document `path:line` whose text changed, quoted before and after; `files:`, each path under `tests/` the step writes, at most five; and `view:`, one `.pyi` per own-code module the files import. Done: the files' tests green after; each test changed or removed cites the moved line it rests on; no test changes that no moved line reaches; a test is removed only when no document line holds its claim; a helper under `tests/support/` whose documented behavior moved changes with its own tests. Its report adds `MOVED <test id> | <path:line>` and `REMOVED <test id> | <path:line>`.
- A `stub` brief has one shape for every builder: the word `stub`, the plan step's text, and the stub paths; no red test. A `stub` step stops after writing and reports; it runs no gate and fixes nothing, since raise-only bodies with no tests fail the planned gates by construction. It lands, with its red tests, in the commit of the build step that turns those tests green, since `make check` runs before every commit and a red test fails it; the red run the orchestrator certified is quoted in that commit's message.
- A brief to a builder, `core-builder`, `seam-builder` or `gatesmith`, may carry one `exclude:` line naming paths the step does not write. The line only removes paths from the step's scope and never adds one. A brief with no such line keeps the scope the step shape fixes.
- A `gatesmith` gate step builds the gate script and the checker's settings and verifies them on the red tests its brief names, and on nothing else: it runs no gate over the tree and does not touch the `Makefile`. A module step takes the same rails: it builds the one module its brief names by path and spec section, verifies it on the red tests its brief names, runs no gate over the tree and does not touch the `Makefile`. Wiring is a `wire` step of its own, with no red test: its brief is the word `wire` and one built gate named by its quality-spec section and bullet, and it adds that gate's `check` and `check-tests` lines to the `Makefile`, then runs `make check` in full and lists in `.gitignore` each path the gate's tool writes into the tree. The orchestrator dispatches `wire` only once a run of that gate over the tree is known to fit the gate's cap. The run that measures it takes the gates' own host-safety rules: at most half of `nproc`, under `gates/heavy.py`, with a hard cap; a run that hits the cap is reported as a finding, and the cap is never extended. A gate step that wires its own gate puts a half-built gate over the whole tree at its first `make check`; a gate verified on its red files alone cannot.
- A reviewer drops only what a gate `make check` currently runs would report, read from the `Makefile` `check` target alone; a gate not yet built catches nothing, so the reviewer files it. `test-reviewer` opens no script under `gates/`. `diff-reviewer` takes its diff only over the paths it reviews, `gauntlet/`, `gates/`, `pyproject.toml`, `uv.lock`, `Makefile`, `.pre-commit-config.yaml`, `.gitignore` and the root `conftest.py`, and lists every other path in the diff unread.
- Every role may return the `OVERLOADED:` shape of `~/dev/CLAUDE.md` 7.1f in place of its report block, before any work or at a safe point partway, and that return is a refusal, not a failure.

## Build order

One agent per dispatch, one diff read, one commit. `role-author` gets no red test; the dispatch proof of the agent it writes is the acceptance line.

1. `CLAUDE.md` and `role-author`, both hand-written.
2. `role-author` writes `diff-reviewer`, `test-reviewer`. Proof: a steered brief returns `REJECTED: STEERING` quoting the line; a clean brief on a planted shortcut returns one anchored finding.
3. `role-author` writes `test-writer`, `mutant-hunter`. Proof: on one quality-spec gate behavior, `COMMANDS` shows no read under `gauntlet/` or `gates/`, and each test's summary line shows `AssertionError` or `NotImplementedError`.
4. `role-author` writes `spiker`, `gatesmith`. Proof: `spiker` closes one remaining M0 item with `podman ps -a` showing its container gone; `gatesmith` takes one gate step, whose red files pass with `git diff HEAD -- Makefile` empty, then that gate's `wire` step, whose `make check` passes.
5. `role-author` writes `core-builder`, `seam-builder`. Proof: a test per agent that its body names only paths inside its scope. Live proof at M1 for `core-builder` and M2 for `seam-builder`.
6. `role-author` writes `architect`. Proof: a brief that dictates a module or an interface returns `REJECTED: STEERING` quoting the line; a clean brief on one multi-piece task writes one design file under `docs/superpowers/specs/`, and `git status --short` shows nothing else.
7. `role-author` rewrites `test-writer`'s red brief to carry a run of behaviors. Proof: the first live red dispatch of two or more behaviors, its `COMMANDS` showing no read under `gauntlet/` or `gates/`; each behavior's tests red as `AssertionError` or `NotImplementedError`; each `replaces:` test gone from the diff; `CHANGED` equal to the lead's count of the diff. A failed proof returns red briefs to one behavior until the role is fixed.
