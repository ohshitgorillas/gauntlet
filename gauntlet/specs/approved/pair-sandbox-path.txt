why the stubs miss it, since the last three rounds turned on them. The command text is held fixed and the caller varied, so a table keyed on text has one entry and one answer, and one answer cannot be both 1 and 3. A table keyed on the caller as well escapes only two ways: fabricate the driver's stdout, which is not a shape this hook has - it answers with a command to run, not with output - or give the reviewer a run whose view of the reviewers' lane differs from the checkout's, which is the per-caller mount policy itself and not a stub of it. The no-op hook gives both callers the checkout as it stands, so both read three round files and both print 3, and the line's reviewer arm fails it. That is also the line's `kills:` exactly, and the defect it names is one a user meets: a blind reviewer reading the rounds other reviewers wrote by running a command instead of calling a tool.

the two expected values are fixture-derived, not design literals. The test seeds the lane with two round files, so 3 is one more than what the checkout holds and 1 is one more than what a masked lane holds; the invariant is that the number reflects what that caller can see, read at two callers (rule 11, property at two inputs). The failure this would file is "a reviewer's shell can see the other reviewers' rounds", which is a bug report and not a diff.
